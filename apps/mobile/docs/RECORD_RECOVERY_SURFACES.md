# Retained record recovery from every app mode

A reopened Build/Preview visit could restore a durable record command, then become stuck: the correct navigation guard blocked changing modes while the command was unresolved, but its retry/acknowledgment controls lived only in the Live renderer. This change moves those controls into a shared `RecordRecoveryPanel` backed by the same existing `RuntimeController`.

`FullAppScreen` owns the panel while Build or Preview is shown, or while a protected original visit is being restored. Live uses the same panel in `RuntimeRenderer`. Within that renderer the page or active record overlay owns it exclusively, so the same command does not get duplicate page/modal controls. The independent retained AppSpec-operation card is preserved. Neither component creates a controller, changes its key, allocates an operation, performs a query on mount, nor restores a command by sending it. Existing read-only `recover()` and all navigation/form/image guards remain unchanged.

The explicit action is labeled **Retry original record request**. It explains that retry may apply the original change if it never completed, using the saved operation ID, input, published version and record revision. This is not described as a read-only outcome lookup. The action calls the existing exact `RuntimeController.retry()` path. A definitive failure offers **Acknowledge record failure**, which calls the existing local acknowledgment path. An unknown result cannot be acknowledged or discarded. Sending shows progress without another action. Storage-clear failure remains visible and retains the entry. Existing local dirty-form navigation confirmation remains after acknowledgment where applicable.

The small presentation/action helper checks current pending status and operation identity when a rendered button is used, so a stale callback cannot operate on a replacement command. UI busy state belongs to an opaque attachment token. A controller A → B → A prop cycle installs a fresh idle attachment, so an old A action cannot leave the returned A busy or clear a newer action. Detaching releases the controller reference; old callbacks and late completions cannot change a replacement attachment. This is defensive reusable-component lifecycle hardening; a supported current-host A → B → A route cycle has not been established. Runtime/backend authority and receipt handling are unchanged; access denial clears the private runtime/host display, account disposal fences late responses, and the original account-scoped stored command is retained for authorized recovery. Original request values and IDs are not displayed by this panel.

## Local evidence

Nine new groups use actual `FullAppController`, `RuntimeController`, `FunctionRuntimeAdapter`, scoped durable command stores and the real navigation guard with injected RPC/atomic-storage ports. A real retained patch envelope binds version 1, record ID and revision 7, while the reopened app is on version 2. Restoration makes zero execution requests and allocates zero new IDs. The tests exercise exact user-triggered retry, lost response, definite rejection and acknowledgment, receipt-clear and acknowledgment-clear failure, stale callbacks, access denial and late account disposal.

The actual `FullAppScreen` is server-rendered in Build, Preview, Live and protected-visit recovery states; each exposes one control for that original record command. Expo focus/back hooks and safe-area plumbing are inert test boundaries for those render checks. Real navigation guards are tested separately without relaxing them. The precise initial Build regression fails against the exact baseline `FullAppScreen.tsx` (zero available retry controls), then passes with this correction. Its failed baseline log is retained in the frozen temporary stage.

Two additional lifecycle groups use the real retained controller command with the pure UI gate coordinator. They exercise A → B → A while a retry is pending, no automatic replay, stale tokens, duplicate clicks, a late old completion during a newer exact retry, cleanup, subscriber removal and account disposal. No mounted React renderer or DOM test dependency is installed; these are coordinator lifecycle tests, not mounted UI or browser proof.

All 667 local tests pass (656 baseline plus nine recovery groups and two lifecycle groups), with zero skips/todos. TypeScript, Expo ESLint with zero warnings, and Prettier pass. This is local controller/render evidence, not browser interaction, native Modal-portal, device or Cloud proof. The actual native/browser record-overlay presentation still needs host verification; server rendering does not execute that portal. Root must export and package the final combined source. No persistent edits, Git writes, Cloud/provider calls, dependencies or native/device actions were performed. The published-customization slice is unchanged except for the intentional recovery-panel delta in `FullAppScreen.tsx`.
