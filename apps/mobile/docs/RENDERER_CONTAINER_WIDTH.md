# Responsive renderer content-width correction

B04's desktop split made the existing global-window assumptions visible. At a 1280-pixel window, the preview is 900 pixels wide and its padded page content is 868 pixels wide. The previous `Math.min(window.width,1200)-32` passed 1168 into `pageRows`, incorrectly pairing a supported Planner Today page set to `twoColumn`. A 520-pixel table inside an 850-pixel window likewise used the desktop table because it checked the window's 850 pixels.

`RuntimeRenderer` now measures its actual row-content region with React Native `onLayout`. That region is inside the existing scroll content padding and max width, so no viewport or padding estimate is needed. `DesignCanvas` measures its padded inner row region the same way. Each `RecordTable` measures its own body inside the surrounding panel, so panel padding, split columns and design-frame borders are naturally included. The small shared `useContainerWidth` hook records finite nonnegative measurements locally; unknown/hidden width uses the conservative narrow layout, and malformed measurements cannot replace a known width. The 960-pixel page and 640-pixel table thresholds are unchanged. The existing device font-scale fallback remains in effect.

No controller, preview factory, adapter, navigation, selection, command, permissions, record or image behavior changes. Width measurement is local presentation state and adds no controller/session keys or resets. Banner presentation already measured its own width and continues to do so. All window-width decisions in these renderer/design-canvas regions have been removed; the remaining window hook reads only font scale.

Four new local test groups cover the actual supported Planner Today `twoColumn` configuration at measured 868/1000 pixels, table width 520/639.75/640/868 pixels, hidden and malformed measurements, large text, injected React Native layout-event callbacks, and the actual React Native Web table component's conservative initial render despite a global 1280-pixel window. The latter rendered-component regression fails against the exact baseline `views.tsx` and passes with the correction; `baseline-table-failure.log` is retained in the frozen temporary stage. The supported Planner test also reproduces the prior incorrect pairing using its original 1168-pixel calculation.

All 645 local tests pass (641 baseline plus four new groups), with zero skips/todos. TypeScript, Expo lint with zero warnings, and Prettier pass. React/Expo 58 documentation and installed React Native 0.88 `LayoutChangeEvent` / `onLayout` types were checked. These are injected layout and server-render unit checks, not a browser resize, CSS-only viewport claim or physical-device receipt. Root still needs to verify the combined export at the reported desktop/850-pixel layouts and rebuild final native artifacts. No persistent edits, Git, Cloud, provider, UI automation, dependency or native/device actions were performed.
