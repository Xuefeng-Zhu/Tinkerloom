# Current-location entry-page aliases during a confirmed save

The exported-665 browser receipt `docs/evidence/2026-10-28/browser-published-inspector-recovery-665.json` records a successful explicit published-version copy followed by a stale local “Resolve the retained operation before opening this app link” warning. Reload removed the warning. This source correction prevents that specific false warning; it does not clear arbitrary local errors.

The supported sequence is reproducible without a browser: `FullAppController.editPublishedVersion()` sends its durably retained exact save, receives the matching acknowledgment, confirms local journal removal, disposes runtime A, then loads fresh authority/capabilities. That load installs runtime B while the host is still `busy`. `FullAppScreen` reruns its route effect for B. A valid initial `?mode=build` request omits the default page, while B's current location is `{pageId: "journalPage"}`. The old canonical guard compared serialized route keys, considered those identities different, and entered the busy/retained-operation warning branch. The warning was not tied to an actual retained entry, so successful completion did not remove it.

`isCurrentFullRoute()` first preserves the original exact canonical-key match, including legacy record URLs whose canonical page is omitted. Its only additional equivalence is an omitted-page request with no record ID or edit state, in the same mode, while the current location is the validated declaration's entry page with no selected record or edit state. A request containing a record ID must retain the existing authorized resolver: an omitted page can select its matching details or form page rather than the entry page. The existing locked-current-location no-op guard uses that comparison. An alias of the location already visible remains there without issuing a request, navigating, allocating a command, clearing another error, or creating a deferred navigation replay. The valid omitted-page URL can remain an alias until ordinary route application/local navigation canonicalizes it.

A different page, selected record, edit flag, mode or invalid request cannot use this no-op. An explicit deferred external attempt is still excluded from the guard. The existing fresh `controller.load()` before `runtime.applyLocation()` remains unchanged for true incoming page/record requests. Runtime pending, form/image busy, dirty-input/flush/discard, current-role checks and account/scope fences are unchanged.

Effect cleanup is deliberately not substituted for intent cancellation in this narrow correction: the existing guarded dirty-route path restores the current URL before awaiting a draft flush. That internal URL change may clean up the React effect while the approved original intent is still pending. Existing `NavigationEpoch`, focused state, host lifetime and runtime identity continue to fence that intent. Any separate obsolete-continuation race needs its own supported ordering and must preserve that restore-before-flush behavior.
