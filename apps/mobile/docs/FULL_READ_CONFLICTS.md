# Bounded retries for full-app reads

An actual hosted `spec.getApp` read and browser refresh completed with a definite `transaction_conflict` HTTP 409. The live runtime adapter already had its own read-conflict handling, but the full-app controller's direct reads did not use it. This source correction covers only the four direct `spec.getApp`, `spec.capabilities`, `spec.review`, and `spec.getGeneration` call sites.

Each read snapshots and deeply freezes its plain JSON request once. At most two additional attempts reuse that same object after 100 and 200 milliseconds. Only an actual `BackendError` with service kind, numeric status 409, exact `transaction_conflict` code and `uncertain === false` qualifies. Raw errors, unknown outcomes, malformed responses or status/certainty values, other conflict codes, denials and missing resources do not repeat. The current controller sequence, open controller and active account-scoped host lifetime are checked before every dispatch and after either settlement. A superseded read returns an internal cancellation marker before DTO parsing, state installation or another HTTP request. Existing authority/install checks remain in place.

No mutation, provider guidance, journal, new operation ID, draft/publication concurrency expectation or transport classifier changes. Runtime adapters continue to receive the original raw transport, so their existing retries are not nested inside this helper. No automatic replay is added to retained commands.
