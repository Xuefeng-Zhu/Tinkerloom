# Committed app activity

The activity screen uses only `spec.listActivity`. It does not load a definition,
private candidate, record, account directory or provider. Open it from Sharing →
Activity, or `/apps/<appId>/activity` after authentication. Existing role and
archive rules are unchanged. All four current app roles can read this metadata,
including archived apps; workspace membership alone is insufficient.

Request:

```json
{ "op": "spec.listActivity", "appId": "app-id", "limit": 50 }
```

Later pages add the exact opaque `cursor`. The response contains exactly
`{appId,items,nextCursor}`. Each item contains exactly
`{id,action,createdAt,status:"committed"}`. IDs identify only this app's audit
entries. No actor, operation/request ID, record ID, draft/spec, record values,
notification content or arbitrary audit columns are exposed. The screen uses
readable labels for known actions and localized times. Unknown future action
names remain valid metadata and display as “App change.”

The existing private `audit.app` index supports one bounded page read of at most
51 selected-column rows for the maximum 50-item response. The service retains
the RowStore's ascending stable entry-ID order; it does not claim chronological
ordering of hashed IDs. No new schema, index, direct table permission, storage
object, key, worker mode or mutation is introduced. Times come from the server's
committed audit metadata and are normalized using the strict AppSpec timestamp
codec. Appwrite metadata datetime precision remains the existing schema's
precision; this does not change lossless record-field timestamp projections.

Every page uses the app/workspace transaction guard and current authorization.
The cursor binds actor, app, workspace, page size, control revision and anchor.
Different scope/input rejects; a supported app change or missing/foreign anchor
requires refreshing the first page. Revocation racing with the read prevents a
mixed-authority response. Corrupt parent/order/time metadata fails closed.

`ActivityController` requires an explicit account ID and session epoch, live
session reader and subscription, and an ordinary authenticated transport. It
checks before dispatch and after settlement, immediately clears on account or
epoch change, and rejects late pages. A current app 403/404 clears app history
without signing out the whole account. A 401 clears history and expires the
session. Stale cursors clear paging; transient errors remain visible. The
controller has no write method or automatic retry. Refreshing cannot replay a
business command.

The route owns the controller. Its removable retain lease supports React's
repeated effect setup without leaking subscriptions from abandoned renders;
focus loads a fresh first page and blur invalidates pending reads. Role/access
checks remain server-side. This history is a paginated view of metadata, not a
replay log, historical data snapshot, backup or notification delivery receipt.

Local evidence: 10 actual Dart `PlatformService`/`MemoryStore` groups and 16
client contract/controller groups. The service fixture is generated by:

```sh
# From appwrite_backend, using Dart 3.11.
dart run test/export_activity_wire.dart ../apps/mobile/src/activity/fixtures/serviceWire.json
dart test test/activity_test.dart
# From apps/mobile.
node --import tsx --test src/activity/activity.test.ts
```

The fixture is repeatable with a fixed server test clock and stable operation
IDs. Tests cover all roles, archived reads, scoped/bounded paging, stale or
foreign cursors, revocation during a read, privacy fields, strict timestamps,
account/late-response races and lifetime cleanup. These are local service and
synthetic client tests. Exact deployed Cloud read/permission acceptance and
mounted browser/native interaction remain separate checks.
