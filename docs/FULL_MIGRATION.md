# Full AppNest → Tinkerloom migration contract

This is the durable checklist for the user's goal: **finish the whole migration to React Native and Appwrite**. Completing another vertical slice does not complete this goal. The target is the original implemented AppNest product contract, the existing Tinkerloom extensions, and the separately identified migration acceptance gates below. Serverpod and Flutter remain references, not runtime dependencies of the replacement.

Baseline inventory: October 28, 2026, Tinkerloom `2234d11`. This document records requirements and evidence boundaries; it is not a declaration that the migration is finished. Update row status only with implementation references and fresh evidence. Preserve failures and historical receipts.

## Status, ownership, and evidence rules

- **Partial**: a bounded replacement exists, but does not satisfy the full row.
- **Missing**: the active replacement has no corresponding complete implementation; retained reference source does not count.
- **Unverified**: implementation or an environment prerequisite exists, but the required acceptance has not run successfully.
- **Additional gate**: migration/readiness work, distinguished from functionality the original application actually delivered.
- **Original exclusion**: intentionally outside the original implemented contract; do not silently turn it into required parity or claim it already existed.
- **Complete** may be recorded only when the row's contract, appropriate negative/concurrency/recovery cases, and required local/live/client/device evidence all pass. None of the broad parity rows below is complete at this baseline.

Owners are durable work areas: **Spec** (shared contract and codecs), **Backend** (trusted Function/data/worker services), **RN** (React Native host/renderer/controllers), **Ops** (packaging/cloud/build/import operations), and **QA** (independent acceptance). They do not refer to a particular temporary agent. Dependencies use the implementation phases in the next section. A row spanning several areas needs coordinated evidence rather than a single owner declaring the whole boundary passed.

Every final-audit receipt must identify the row ID, source commit, command/scenario, date, actual runtime/deployment/build, expected and observed results, and a repository evidence location. Identify synthetic adapters and fake stores explicitly. A screenshot alone does not prove storage, authorization, durable workers, device execution, or numeric assertions. A JavaScript export is not a native build; a native build is not an installation/device test. Historical AppNest results supply test ideas, never Tinkerloom passes.

Integrated account lifetime, final full-host/device execution and full app recovery remain separate gates; the native module compilation checkpoint below is distinct.
- [Native compilation checkpoints](NATIVE_VERIFICATION.md): the older baseline is preserved. The row baselines below are historical inventory. None of these implementation checkpoints completes the full parity, Cloud, mounted-client, worker, media, migration or device acceptance matrix.

## Reusing pure Dart AppSpec in the Function

The active [appnest_spec package][spec-package] is byte-identical to its retained legacy copy at this inventory: 34 source/fixture/schema/test/tool files excluding caches. Its ten `lib/` files total about 131 kB. Runtime imports are `dart:convert` and `package:crypto/crypto.dart`; there is no Serverpod, Flutter, database, HTTP, native bridge or storage dependency. `tool/export.dart` uses `dart:io` to produce schema/fixtures and is not a runtime requirement. The contract, parser, canonicalization/hash, compatibility/diff, semantic patches, query/aggregate validation, capability registry and template definitions are good reuse candidates.

This is a portability assessment, not a successful Cloud build. The package currently declares `resolution: workspace` and SDK `>=3.13.0 <3.14.0`, while the deployed Function uses Cloud Dart 3.11. Copying that pubspec unchanged into the Function will not resolve. The Function's current `>=3.5.0 <4.0.0` constraint does not override its dependency's SDK requirement.

Required implementation/verification sequence:

1. Make the active shared package independently resolvable with an explicitly tested Cloud-compatible SDK constraint; preserve `legacy_appnest` as reference. Run all eight spec test files and golden fixtures on the actual intended SDK. Do not merely lower a version string and declare compatibility.
2. Bundle the package **inside the uploaded Function source root**, for example as `packages/appnest_spec` with a local path dependency. A deployment archive containing only `appwrite_backend/` cannot resolve a sibling `../packages` outside that archive. Keep package assembly reproducible and verify copied source hashes to prevent a stale vendor copy.
3. Include runtime sources and required dependency/lock metadata; omit caches, unrelated Flutter/Serverpod packages, ignored config and credentials. Verify entrypoint/build commands and archive root on Appwrite with the new dependency before relying on it.
4. Run the original parser/canonical/compatibility tests unchanged where valid, then add Cloud-runtime and cross-language fixtures. Parse acceptance does not establish Function services, transaction semantics, RN rendering or effects.
5. Design an explicit codec for existing flat Tinkerloom definitions and its civil-date/long-text extensions. Preserve old stored request/response receipts and published behavior. Full AppSpec optional normalization and larger limits must not silently rewrite existing bounded records.
6. Reconcile envelope limits: original AppSpec permits 128 KiB, while the current Function request/definition/value/receipt bounds are smaller. Validate the entire transport→parser→storage→response chain, not just the shared parser. Preserve coherent bounds for queries, media and provider responses independently.
7. Keep runtime-local helpers in the correct environment. `resolveViewQuery` and sample helpers use local `DateTime`; a UTC Cloud host is not the user's timezone. Send/validate explicit local-day boundaries or a reviewed timezone contract and test DST.

Source reuse must not import SQL/Serverpod services or Flutter rendering. [Original service modules][original-modules] are behavioral references; Appwrite needs its own authorized transaction/unique-identity/index/reconciler implementation, and RN needs its own semantic renderer. The full shared package's typed schema can generate/check a TypeScript contract, reducing independent normalization drift; generated models must not replace server authority or client input-state handling.

### Full builder routing checkpoint

The authenticated `/workbench` and `/apps/[appId]/full` routes now use the
full launcher, visual/JSON builder, isolated previews, explicit publication
review and durable exact-request recovery. The account registry uses endpoint,
project, account and app scopes. Transport checks authentication epochs before
dispatch and after settlement, including same-account sign-out/sign-in; a late
401 cannot expire a replacement account. New app navigation opens the full
workbench; existing bounded app routes remain available. Client verification:
224 tests, lint, typecheck, formatting and all three Expo exports passed.
Integrated live full-engine flows and final-source native interaction remain
unverified; this checkpoint does not mark the migration complete.

### Inbox, access metadata and wire-contract checkpoint

The authenticated inbox and builder reminder-run routes are integrated with
account-epoch-fenced transport and encrypted exact read-receipt recovery.
Notification links hydrate and verify the current authorized record before
navigation; closed accounts cannot receive late results. Pending reminder
states remain distinct from confirmed scheduling or delivery. Engine-neutral
metadata supports shared links, sharing and archived receipt recovery without
hydrating author-private definitions. Full and bounded routes select the correct
engine. Current operational capabilities initialize a new runtime; unrelated
record changes preserve dirty forms, and a later publication stays marked
outdated until explicitly resolved.

A deterministic Dart exporter now produces the React Native service fixtures.
CI checks them against the actual service; this caught and corrected an editor
capability-name mismatch. The new wire tests use the simulated store and do not
represent Cloud proof. Combined client verification passed253 tests with0skips,
lint, typecheck, formatting and all three Expo exports. Five new metadata service
tests and the wire comparison pass on Dart3.11. Live full-engine/inbox/worker/media
and final-source native interaction remain required.

### Foreground semantic refresh checkpoint

The [watch contract](../appwrite_backend/WATCH.md) negotiates authenticated
foreground polling at no less than15seconds. It exposes only current app/version,
semantic revision, role and archive state. Renewed transaction guard nonces never
become watch tokens. The client backs off to120seconds, pauses while hidden or
backgrounded, fences late account responses, coalesces in-flight refreshes and
defers record reloads while a form or retained command is unresolved. It never
automatically replays mutations. Confirmed authority changes hide private data
before a subsequent manifest read can fail. Expo focus leases also release
polling/device controls for routes retained behind sharing and inbox screens.

Client verification passed272 tests, lint, typecheck, formatting and all three
platform exports; read-only watch/media-usage classification has separate focused
coverage. The backend retained118 service groups,307 combined tests and87 AppSpec
tests, adds11 watch tests, and compiles both AOT entry points on Dart3.11. These
are local transport/store/lifecycle proofs; actual Cloud watch timing and native
foreground behavior remain separate gates.

### Offline import and hosted provisioning checkpoints

[Import preflight](IMPORT_DRY_RUN.md) is a strict offline planner and simulated
resume ledger. It validates real AppSpec/record semantics, explicit identity
mappings, source/target hashes, dependencies and capacity plans. Thirty-two
checks and a7→36-operation synthetic restart passed. It has no network/apply
adapter and accepts no credentials. Real export, account recovery, media/history
strategy and approved cutover remain unverified; quarantine is not import success.

The Free project now has30 tables with private permissions/row security, all
expected columns/bounds/indexes available, and one private media bucket. The
[bounded schema receipt](evidence/2026-10-28/full-schema-20261028.json) preserves
two equivalent original workspace string columns and the initial incomplete
console-scrollback audit. No table or data was replaced. The private worker
built fromb542d9f is active with execute[] and no domains, a60-minute recovery
interval and120-second timeout. Its [configuration receipt](evidence/2026-10-28/private-worker-20261028.json)
is provisioning/build evidence, not worker/media delivery acceptance. The core
built fromfc71fe4 is now active; full REST acceptance is running separately.
